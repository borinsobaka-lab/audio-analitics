# Audio Analytics — речевая аналитика офлайн-продаж

Сервис записывает рабочий день на ресепшене студии, распознаёт речь
(русский/грузинский/английский) и с помощью LLM строит отчёт: сколько было
продаж, соблюдался ли скрипт, сколько предлагали апсейлов, рекомендации
менеджеру.

## Архитектура

```
[Десктоп-клиент Tauri (Win/macOS)]
   запись микрофона → Opus-чанки по 5 мин → фоновая загрузка
        ▼
[FastAPI на Hetzner]  →  [Cloudflare R2: аудио]  →  [Celery-воркер]
        ▼                                              │
[Supabase Postgres]  ◄─────────────────────────────────┘
        ▼                 пайплайн: ffmpeg → Silero VAD → ElevenLabs Scribe
[Веб-дашборд React]                → Claude (сегментация → разбор по скрипту → итог дня)
```

| Каталог | Что это |
|---|---|
| `backend/` | FastAPI API + Celery-пайплайн обработки + CLI |
| `dashboard/` | Веб-дашборд: сводка за период, разборы смен, **метрики анализа**, менеджеры |
| `desktop/` | Tauri v2 приложение записи (Windows/macOS) |
| `docs/prompts/` | Эталонные промпты метрик — копируются в админку |
| `.interface-design/` | Система интерфейса админки: токены, шкала, компоненты |

Иконки сайта лежат в `dashboard/public/`. Исходник один — `favicon.svg`;
`favicon.ico`, `apple-touch-icon.png` и `icon-512.png` получены из него
растеризацией, поэтому при смене знака или фирменного цвета правится сначала
SVG, а растры перегенерируются.

Перед правкой вёрстки дашборда читайте `.interface-design/system.md` —
значения оттуда переиспользуются, а не выбираются заново.

## Менеджеры и сессии записи

Менеджеры заводятся в админке на вкладке «Менеджеры». Активные попадают в
выпадающий список приложения — менеджер выбирает себя перед началом дня, и
отчёт подписывается его именем. Деактивированный менеджер исчезает из списка
приложения, но остаётся в системе, чтобы прошлые отчёты не потеряли автора.

Запись за дату не уникальна: если приложение вылетело и было запущено заново,
незакрытая сессия продолжится (сегменты допишутся в неё), а после завершённого
дня повторный старт создаст **отдельную сессию и отдельный отчёт**. В админке
для каждой записи доступны «Завершить принудительно» (закрыть сессию, которую
приложение не закрыло само, и обработать загруженное), «Обработать заново» и
«Удалить» (безвозвратно, вместе с аудио в R2).

## Метрики и анализ

Анализ дня управляется **метриками** — их заводит владелец в админке
(раздел «Метрики и анализ») в любом количестве. Метрика = название + промпт
(инструкции: что оценивать, эталонный скрипт, критерии) + шкала (5- или
10-балльная). Каждый разговор дня прогоняется через каждую активную метрику:
ИИ решает, применима ли метрика к разговору, ставит оценку и перечисляет,
что сделано хорошо и что плохо.

В списке дней у каждого отчёта видны срабатывания и средние оценки
(«Качество продажи: 4 · ★ 7.2/10»), в отчёте дня — плитки по метрикам,
а в каждом диалоге — детальные оценки с плюсами/минусами и кнопкой ▶,
которая проигрывает аудио с начала диалога. Правка метрик применяется к
следующему обработанному дню; старый день можно пересчитать кнопкой
«Обработать заново».

Готовые промпты под скрипт студии лежат в `docs/prompts/`: «Встреча и
выявление цели» (первый контакт до занятия) и «Качество продажи абонемента»
(разговор после занятия). Они разделены намеренно — между этапами проходит
занятие, поэтому в записи это всегда разные разговоры, и калибруются они
независимо. Обе создаются автоматически при `python -m cli.seed`.

Служебные промпты (сегментация дня на диалоги и итоговая сводка дня)
встроены в пайплайн и не требуют настройки.

## Дашборд и стоимость обработки

Раздел «Дашборд» отвечает на вопрос, на который разбор одной смены ответить не
может: растёт менеджер или проседает. Любой показатель за выбранный период
стоит рядом со своим значением за предыдущий период такой же длины — пресеты
(7 дней, 30 дней, этот и прошлый месяц), произвольный диапазон и фильтр по
менеджеру.

Динамика показана **малыми кратными** — по одному графику на показатель. Это не
оформление: метрики бывают пяти- и десятибалльные, и общая ось дала бы ложное
сравнение.

После каждой обработки в смену записывается её **стоимость** — минуты
распознавания и токены модели хранятся отдельно от суммы, поэтому при смене
тарифов прошлые смены можно пересчитать. Тарифы задаются в `.env`
(`PRICE_ASR_PER_HOUR_USD`, `PRICE_LLM_INPUT_PER_MTOK_USD`,
`PRICE_LLM_OUTPUT_PER_MTOK_USD`). **Цену часа распознавания обязательно
поставьте свою** — значение по умолчанию ориентировочное, и с ним админка
будет показывать убедительно выглядящие, но неверные суммы.

В карточке смены показана стоимость последней обработки: «Пересчитать»
запускает распознавание и анализ заново и тратит деньги ещё раз.

## Быстрый старт

### 0. Что подготовить

- Ключи API: **ElevenLabs**, **Anthropic** (обязательно); Supabase-проект;
  R2-бакет в Cloudflare.
- В Supabase SQL Editor выполнить миграции по порядку:
  `backend/migrations/001_initial.sql`, `002_multiple_sessions_and_managers.sql`,
  `003_analysis_metrics.sql`, затем `004_processing_cost.sql`.
  На уже развёрнутой базе достаточно выполнить только новые миграции — они
  безопасны для повторного запуска.

### 1. Бэкенд локально

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp ../.env.example .env   # заполнить значения
python -m cli.seed --org "Моя студия" --location "Точка 1"
# → печатает location_id; сгенерировать ключ и вписать DEVICE_API_KEYS в .env
uvicorn app.main:app --reload            # API на :8000
celery -A app.celery_app.celery worker --loglevel=info   # в соседнем терминале
```

Требуется `ffmpeg` в PATH и Redis (`docker run -p 6379:6379 redis:7-alpine`).

### 2. Этап 0 — проверка гипотезы без приложения

Записать реальный день диктофоном/конференц-микрофоном и прогнать локально:

```bash
cd backend
python -m cli.stage0 путь/к/записи.mp3            # полный пайплайн
python -m cli.stage0 запись.opus --skip-llm       # только VAD+ASR (дёшево)
```

Результат: `transcript.txt`, `analysis.json`, `report.md` рядом с файлом.
Это главный шаг: он показывает, распознаётся ли грузинский в вашей акустике,
до написания какого-либо продукта.

### 3. Дашборд

```bash
cd dashboard
npm install
npm run dev        # http://localhost:5173, проксирует /api на :8000
```

### 4. Десктоп-клиент

Что должно быть установлено на машине сборки:

| Инструмент | macOS | Windows |
|---|---|---|
| Компилятор C | `xcode-select --install` | Build Tools for Visual Studio (C++) |
| Rust | `curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs \| sh` | rustup-init.exe с rustup.rs |
| Node.js LTS | nodejs.org или `brew install node` | nodejs.org |
| **CMake** | `brew install cmake` | входит в Build Tools / cmake.org |

CMake обязателен: крейт `opus` собирает libopus из исходников. Без него сборка
падает с `is cmake not installed?`. После установки инструментов открыть новое
окно терминала (обновится PATH).

```bash
cd desktop
npm install
npm run tauri dev            # разработка
npm run build:mac            # сборка под архитектуру этой машины
npm run build:mac:universal  # сборка сразу под Apple Silicon и Intel
```

Готовое приложение: `desktop/src-tauri/target/release/bundle/`
(`macos/Audio Recorder.app` и `dmg/`), для универсальной сборки —
`target/universal-apple-darwin/release/bundle/`.

#### Маки на Intel

Обычная сборка содержит только архитектуру машины, на которой собиралась.
Приложение, собранное на Apple Silicon, **на Intel не запустится**: Rosetta
переводит только в одну сторону — Intel-код на Apple Silicon, не наоборот.

Один раз на машине сборки:

```bash
rustup target add x86_64-apple-darwin aarch64-apple-darwin
```

Дальше собирать `npm run build:mac:universal` — получается один `.app` под обе
архитектуры. Скрипт в конце печатает `lipo -archs`, там должно быть
`x86_64 arm64`.

Требуется macOS 11 Big Sur или новее (`minimumSystemVersion` в
`tauri.conf.json`) — это Intel-маки примерно с 2013 года. Версия проверяется
в «Об этом Mac».

В настройках приложения указать адрес сервера и ключ устройства
(из `DEVICE_API_KEYS`). Кнопки: начать день / пауза (личный разговор) /
завершить день (дозагрузка чанков → сервер запускает обработку).

- **macOS без подписки Apple Developer:** собирать локально на Mac
  (`signingIdentity: "-"` уже настроен) и переносить `.app` через
  AirDrop/флешку. На машине, куда перенесли, macOS пометит приложение
  карантином и откажется его открывать («повреждено»), потому что подпись
  ad-hoc, а не Developer ID. Снимается один раз:
  `xattr -cr "/Applications/Audio Recorder.app"`.
- **Доступ к микрофону выдаётся заново на каждой машине** — при первом запуске
  система спросит разрешение. Если окно не появилось, проверить
  «Системные настройки → Конфиденциальность и безопасность → Микрофон».
- **Windows без сертификата:** в SmartScreen «Подробнее → Выполнить в любом
  случае».

### 5. Продакшн на Hetzner

```bash
# на сервере, в корне репозитория:
cp .env.example backend/.env   # заполнить прод-значениями
docker compose up -d --build
```

Перед сервисом поставить Cloudflare (DNS + TLS) на порт 8000; дашборд собрать
`npm run build` и раздавать статику (Cloudflare Pages или nginx).

## Как работает пайплайн обработки

1. Клиент грузит Opus-чанки → по «Завершить день» сервер ставит задачу в Celery.
2. Чанки склеиваются (ffmpeg, без перекодирования), считается длительность.
3. **Silero VAD** находит речевые участки; тишина/музыка выбрасываются
   (обычно остаётся 2–4 ч из 12).
4. Речевые участки склеиваются в один файл и уходят в **ElevenLabs Scribe**
   (диаризация + пословные таймкоды); таймкоды маппятся обратно на исходную
   запись.
5. **Claude, этап 1** (`dialog_segmentation`): транскрипт дня → список диалогов
   с типами (продажа/консультация/отказ/сервис/нерелевантно).
6. **Claude, этап 2** (`sale_analysis`): каждый значимый диалог → чек-лист
   этапов скрипта (✅/⚠️/❌) с дословными цитатами и таймкодами, исход, число
   апсейлов, эффективность.
7. **Claude, reduce** (`daily_summary`): метрики дня + все разборы → главные
   отклонения, рекомендации, предложения по скрипту.
8. Дашборд показывает отчёт; клик по цитате/таймкоду проигрывает аудио с этого
   места (presigned URL из R2).

Нерелевантные (личные) разговоры классифицируются, но их текст не сохраняется.

## Приватность и право (Грузия)

Аудиозапись в помещении регулируется законом Грузии «О защите персональных
данных» (в силе с 01.03.2024): нужны табличка-уведомление для клиентов,
письменное согласие сотрудников, документированная политика хранения
(по умолчанию 60 дней, настроить lifecycle-правило в R2 на тот же срок) и
ограничение доступа. Формулировки согласовать с юристом. В приложении есть
кнопка «Пауза» для личных разговоров.
