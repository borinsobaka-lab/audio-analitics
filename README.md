# Audio Analytics — речевая аналитика офлайн-продаж

Сервис записывает рабочий день на ресепшене студии, распознаёт речь
(русский/грузинский/английский) и с помощью LLM строит отчёт: сколько было
продаж, соблюдался ли скрипт, сколько предлагали апсейлов, рекомендации
менеджеру.

## Архитектура

```
[Десктоп-клиент Tauri (Win/macOS)]
   запись микрофона → Opus-чанки по 5 мин → фоновая загрузка
        ▼
[FastAPI на Hetzner]  →  [Cloudflare R2: аудио]  →  [Celery-воркер]
        ▼                                              │
[Supabase Postgres]  ◄─────────────────────────────────┘
        ▼                 пайплайн: ffmpeg → Silero VAD → ElevenLabs Scribe
[Веб-дашборд React]                → Claude (сегментация → разбор по скрипту → итог дня)
```

| Каталог | Что это |
|---|---|
| `backend/` | FastAPI API + Celery-пайплайн обработки + CLI |
| `dashboard/` | Админка из двух продуктов: **скрипты** администраторов и речевая аналитика (сводка, разборы смен, метрики, менеджеры) |
| `desktop/` | Tauri v2 приложение записи (Windows/macOS) |
| `docs/prompts/` | Эталонные промпты метрик — копируются в админку |
| `.interface-design/` | Система интерфейса админки: токены, шкала, компоненты |

Иконки сайта лежат в `dashboard/public/`. Исходник один — `favicon.svg`;
`favicon.ico`, `apple-touch-icon.png` и `icon-512.png` получены из него
растеризацией, поэтому при смене знака или фирменного цвета правится сначала
SVG, а растры перегенерируются.

Перед правкой вёрстки дашборда читайте `.interface-design/system.md` —
значения оттуда переиспользуются, а не выбираются заново.

## Скрипты администраторов

Админка состоит из двух продуктов, переключатель — в шапке бокового меню:
**Скрипты** (открываются после входа) и **Аналитика** (всё, что описано ниже;
дашборд теперь живёт по адресу `/analytics`).

Скрипты — замена Google-документа «Скрипты LS Tbilisi»: что администратор
пишет клиенту в чат и говорит по телефону. Разделы («Запись на пробное»,
«Возражения», «Частые вопросы»…) — в боковом меню, на телефоне — лентой над
списком. Что умеет раздел:

- поиск сразу по названиям, текстам на всех языках и пояснениям, с подсветкой;
  клавиша «/» ставит курсор в поиск, Esc очищает;
- язык (RU / EN / GE) и студия (Ваке / Сабуртало) выбираются один раз на все
  скрипты и запоминаются в браузере; если перевода на выбранный язык нет,
  карточка говорит об этом прямо и показывает другой язык;
- каждое сообщение копируется одной кнопкой — ровно текст, который уйдёт в чат,
  без пометок «RU:» и «После отправки…»;
- слева от «Копировать» у первого сообщения — значок ссылки: копирует ссылку
  на этот скрипт, чтобы положить её в CRM, базу знаний, чат. По ссылке
  скрипт открывается и подсвечивается; если его перенесли в другой раздел,
  страница найдёт его там;
- карточки всегда раскрыты — всё видно сразу; удалить скрипт можно в правке,
  после двух подтверждений;
- `[день]`, `[время]`, `[сумма]` подсвечены как места, которые надо заполнить;
  ссылки кликабельны;
- подсказки «Как использовать» и «Дальше» оформляются кнопками над полем в
  правке: **жирный**, подчёркнутый, список пунктов и «Ссылка на скрипт» —
  выделенная фраза становится ссылкой на выбранный скрипт (по id, переживает
  переименование), «Добавить копирование» — выделенный текст показывается на
  подложке со значком «Копировать» справа (название скрипта для поиска, текст
  задачи для CRM). Тексты сообщений не форматируются — они уходят в чат.
- `{админ}`, `{студия}` и свои переменные в фигурных скобках подставляются
  сами — имя того, кто вошёл, выбранная студия, значения из настроек — на языке
  текста; и на экране, и при копировании. Задаются в «Скриптах» → «Настройки»:
  названия студий и имена администраторов на трёх языках, свои переменные
  (цены, ссылки, реквизиты) и даты — «через N дней от сегодня», подставляются
  как ДД.ММ («свободные места есть на {слот1} и {слот2}»). Подставленная
  переменная подсвечена синим; оранжевая — подставлять нечего (её нет в
  настройках или нет значения на выбранном языке), подсказка говорит, что
  довнести;
- у каждой карточки внизу — кто, когда и что изменил в последний раз; при
  сохранении правки админка спрашивает «Что изменили?»;
- «Предложить изменения» — тихая кнопка с карандашом на шапке каждого
  скрипта: любой сотрудник пишет, что поправить, а скрипт подставляется сам;
  предложения собираются в «Настройках» → «Предложения» со ссылкой на скрипт. У
  «Настроек» в меню — розовый счётчик новых, у каждого администратора свой:
  гаснет, когда он сам открыл предложения. Сделанное отмечают кнопкой.
- «Настройки» → «Хронология» — каждое создание, правка и удаление скрипта:
  кто, когда, комментарий и только изменившиеся поля «было → стало»,
  удалённые слова подсвечены красным, новые — зелёным. Подгружается порциями
  по 20 при прокрутке.
- «Настройки» → «Статистика» — какие скрипты копируют: каждое нажатие
  «Копировать» у текста скрипта — отметка (кто, когда, на каком языке,
  вариант какой студии). Рейтинг скриптов за период (сегодня, 7 и 30 дней,
  всё время или свои даты), по одному сотруднику или по всем, по одному
  языку или по всем — с разбивкой RU / EN / GE.
- «ИИ-помощник» в панели над скриптами (OpenAI): сотрудник вставляет
  сообщение клиента — ИИ находит подходящие скрипты и показывает их с
  «Копировать» на языке клиента, а если подходящего нет — пишет ответ сам,
  по правилам продаж (скрипт продаж из «Аналитики») и только с фактами из
  скриптов и переменных. Написанный ответ **проверяется вторым, независимым
  запросом**: каждый факт (цены, скидки, сроки, условия, обещания) должен
  подтверждаться базой. Не прошёл — ИИ переписывает с учётом замечаний и
  проверка повторяется (не больше двух попыток); снова не прошёл или данных
  нет — ответ не показывается («недостаточно информации» и чего не хватает).
  Принцип — fail closed: лучше честный отказ, чем выдуманная скидка. База
  передаётся целиком (скриптов десятки — поиск по кускам здесь только мог бы
  пропустить правило). Промпты ответа и проверки и модель — в «Настройки» →
  «ИИ-помощник»;
  ключ — `OPENAI_API_KEY` в окружении бэкенда, модель по умолчанию —
  `OPENAI_MODEL`.

Разделы-звонки. Раздел бывает двух типов: текстовые скрипты (как выше) и
звонок — один сценарий на раздел (под разные звонки — разные разделы; тип
выбирается при создании раздела). Во время звонка администратор читает
реплику с экрана и кликает, что ответил клиент, — сценарий сам ведёт дальше:
слева путь (что уже пройдено и что отвечал клиент, по клику — вернуться),
в центре реплика крупно, подсказка и кнопки ответов (с клавиатуры 1–9,
назад — Backspace), справа возражения и этапы — перейти в любой момент. Имя
клиента вписывается сверху и подставляется в `{имя}`; «Нет нужного ответа»
отправляет случай в «Предложения». Сценарий правится в редакторе (блоки,
текст на трёх языках с форматированием и переменными, ответы с переходами,
новые блоки прямо из ответа) и сохраняется с «Что изменили?» в хронологию.
Стартовый сценарий — холодный звонок «Запись на пробное» из документа
«Скрипт — ЗВОНОК». Нужна миграция `016_call_scripts.sql`.

Аналитика звонков («Аналитика» → «Звонки»). Каждый звонок по сценарию
пишется по ходу разговора, после каждого клика: путь по блокам, ответы
клиента, время на шаге и итог — «Записан», «Перезвонить», «Отказ», «Не
дозвонились» или «без итога» (брошен на середине). Итог ставится сам, если
разговор дошёл до блока с итогом (в редакторе у блока поле «Итог звонка»;
в стартовом сценарии «Запись» — записан, «Перезвоню» — перезвонить), иначе
администратор отмечает его одним нажатием: «Не дозвонились» на первом шаге,
«Завершить звонок» посреди разговора, кнопки итога в конце сценария. На
странице за выбранный период, по сценарию и администратору: конверсия в
запись (из дозвонившихся), итоги звонков, воронка по этапам (сколько
дошли, сколько оборвались без записи, медиана времени на этапе, ответы
клиентов), где обрываются звонки (включая возражения), возражения и
конверсия после них, таблица администраторов, «до каких этапов доходят
администраторы» и журнал звонков с путём каждого разговора. Сотрудник с
доступом «только свои» видит свои звонки. Нужна миграция `017_call_runs.sql`.

Там же:
- «Перезвонить». Над сценарием — имя и телефон клиента; итог «Перезвонить»
  спрашивает, когда перезвонить (через час, вечером, завтра или точное
  время) и комментарий. Открытые перезвоны — кнопка «Перезвонить · N» над
  сценарием: у кого время подошло — сверху; «Позвонить» начинает звонок с
  именем и телефоном, разговор по нему закрывает перезвон сам (не
  дозвонились — остаётся), «Готово» — закрыть вручную.
- «Нет нужного ответа» отмечается на шаге звонка: в аналитике — «Где
  сценарию не хватает ответов» с примерами, что говорил клиент.
- Версии сценария: звонки по каждой редакции (с комментарием правки),
  фильтр по версии — сравнить «до» и «после».
- Студии, часы и дни недели — где и когда звонки идут лучше.
- Цель по конверсии в запись (задаёт тот, у кого доступ ко всему):
  «ниже цели» у администраторов, версий и студий.
- Журнал выгружается в Excel (CSV с теми же фильтрами).
- Связь с записью смены: звонок сотрудника попадает в отчёт его смены
  («Звонки по сценарию» — ▶ слушать с момента звонка), из журнала —
  переход в запись на этот момент. При разборе смены ИИ получает к
  разговору, совпавшему по времени со звонком, пройденные шаги сценария и
  ответы клиента — метрики про следование скрипту сверяют сказанное с ними.
  Время звонка сопоставляется с началом записи смены, поэтому работает для
  сотрудников, а не для входа владельца.

Нужна миграция `018_call_callbacks.sql`.

Скорость открытия. Админка показывает сразу то, что было в прошлый раз
(кто вошёл, скрипты, настройки — в localStorage, отдельно для каждого
входа), и обновляет это в фоне; запросы к серверу стартуют параллельно ещё
до первой отрисовки. Service worker (`dashboard/sw.template.js`, собирается
в `sw.js` со списком файлов сборки) держит оболочку на устройстве: с
рабочего стола и по ссылке она открывается без загрузки, даже без сети.
«Аналитика», настройки и «Сотрудники» — отдельными кусками, догружаются в
фоне. Сервер сжимает ответы (gzip) и разрешает браузеру сутки не повторять
предварительный CORS-запрос.

Читают скрипты и открывают «Настройки» все вошедшие; без права правки
настройки только для просмотра. Правят (добавить кнопкой «+ Скрипт» вверху,
изменить, удалить, перенести в другой раздел, поменять порядок скриптов; у
раздела — «⋯» справа от названия: название, иконка, порядок в меню) те, кому в карточке сотрудника выдано «Скрипты: чтение и правка», и
владелец. Раздел удаляется, только когда в нём не осталось скриптов.

Стартовый набор — перенос документа: `backend/app/playbook_default.json`
(9 разделов, 44 скрипта). Он загружается в базу сам при первом открытии
раздела и ровно один раз; дальше скрипты живут в базе и правятся в админке.
Нужны миграции `010_playbook.sql`, `012_playbook_changes_settings.sql` и
`013_playbook_history_suggestions.sql` (хронология и предложения),
`014_suggestion_item.sql` (предложение привязано к скрипту),
`015_playbook_copies_ai.sql` (статистика копирований),
`016_call_scripts.sql` (разделы-звонки), `017_call_runs.sql` (аналитика
звонков), `018_call_callbacks.sql` (клиент и «Перезвонить»)
(`012` заодно заменяет в уже загруженных скриптах имена из документа —
«Меня зовут Анастасия», «Это Мария» — на `{админ}`).

## Менеджеры и сессии записи

Менеджеры заводятся в админке на вкладке «Менеджеры». Активные попадают в
выпадающий список приложения — менеджер выбирает себя перед началом дня, и
отчёт подписывается его именем. Деактивированный менеджер исчезает из списка
приложения, но остаётся в системе, чтобы прошлые отчёты не потеряли автора.

Запись за дату не уникальна: если приложение вылетело и было запущено заново,
незакрытая сессия продолжится (сегменты допишутся в неё), а после завершённого
дня повторный старт создаст **отдельную сессию и отдельный отчёт**. В админке
для каждой записи доступны «Завершить принудительно» (закрыть сессию, которую
приложение не закрыло само, и обработать загруженное), «Обработать заново» и
«Удалить» (безвозвратно, вместе с аудио в R2).

## Метрики и анализ

Анализ дня управляется **метриками** — их заводит владелец в админке
(раздел «Метрики и анализ») в любом количестве. Метрика = название + промпт
(инструкции: что оценивать, эталонный скрипт, критерии) + шкала (5- или
10-балльная). Каждый разговор дня прогоняется через каждую активную метрику:
ИИ решает, применима ли метрика к разговору, ставит оценку и перечисляет,
что сделано хорошо и что плохо.

В списке дней у каждого отчёта видны срабатывания и средние оценки
(«Качество продажи: 4 · ★ 7.2/10»), в отчёте дня — плитки по метрикам,
а в каждом диалоге — детальные оценки с плюсами/минусами и кнопкой ▶,
которая проигрывает аудио с начала диалога. Правка метрик применяется к
следующему обработанному дню; старый день можно пересчитать кнопкой
«Обработать заново».

Готовые промпты под скрипт студии лежат в `docs/prompts/`: «Встреча и
выявление цели» (первый контакт до занятия) и «Качество продажи абонемента»
(разговор после занятия). Они разделены намеренно — между этапами проходит
занятие, поэтому в записи это всегда разные разговоры, и калибруются они
независимо. Обе создаются автоматически при `python -m cli.seed`.

Служебные промпты (сегментация дня на диалоги и итоговая сводка дня)
встроены в пайплайн и не требуют настройки.

## Дашборд и стоимость обработки

Раздел «Дашборд» отвечает на вопрос, на который разбор одной смены ответить не
может: растёт менеджер или проседает. Любой показатель за выбранный период
стоит рядом со своим значением за предыдущий период такой же длины — пресеты
(7 дней, 30 дней, этот и прошлый месяц), произвольный диапазон и фильтр по
менеджеру.

Динамика показана **малыми кратными** — по одному графику на показатель. Это не
оформление: метрики бывают пяти- и десятибалльные, и общая ось дала бы ложное
сравнение.

После каждой обработки в смену записывается её **стоимость** — минуты
распознавания и токены модели хранятся отдельно от суммы, поэтому при смене
тарифов прошлые смены можно пересчитать. Тарифы задаются в `.env`
(`PRICE_ASR_PER_HOUR_USD`, `PRICE_LLM_INPUT_PER_MTOK_USD`,
`PRICE_LLM_OUTPUT_PER_MTOK_USD`). **Цену часа распознавания обязательно
поставьте свою** — значение по умолчанию ориентировочное, и с ним админка
будет показывать убедительно выглядящие, но неверные суммы.

В карточке смены показана стоимость последней обработки: «Пересчитать»
запускает распознавание и анализ заново и тратит деньги ещё раз.

## Разбор запускается вручную

Приложение закрывает смену и загружает чанки — и на этом останавливается.
Смена появляется в админке со статусом **«Ждёт разбора»** и ничего не стоит,
пока владелец не нажмёт **«Обработать»**.

Так сделано ради денег и тишины в отчётах: автоматический разбор всего подряд
означал бы платить за пустые дни, неудачные дубли, проверки оборудования и
смены, которые никто не собирался смотреть. Теперь разбирается то, что решили
разобрать, — например, только дни конкретного менеджера перед встречей с ним.

Той же кнопкой смена пересчитывается после правки метрик или промптов; на
разобранной смене она называется «Пересчитать». Пересчёт берёт расшифровку с
прошлого разбора и за распознавание речи второй раз не платит; если сама
расшифровка получилась плохой, рядом есть «Распознать заново».

Разбор, статус которого не менялся несколько часов (`STALE_PROCESSING_S`),
админка помечает «Разбор завис»: так выглядит воркер, убитый по памяти или при
передеплое. Такую смену можно запустить заново или удалить — раньше она
отвечала «уже в очереди» вечно.

## Точки продажи

Точка продажи — одна студия с одним ресепшеном. Заводятся в админке, в разделе
«Точки продажи»; к точке привязаны сотрудники, смены и отчёты.

Сотрудники к точкам **не привязаны**: на любой студии в списке приложения
видны все. Смена достаётся той точке, где стоит компьютер, на котором её
начали, — человек может подменять на соседней студии, и ничего перенастраивать
не нужно.

Приложение на ресепшене показывает список точек и запоминает выбор: компьютер
стоит на конкретной стойке и студию не меняет. Раньше там вводились адрес
сервера и ключ устройства — две строки с чужих слов, и любая опечатка
выглядела как «сервер недоступен».

В админке студия переключается выпадающим списком внизу бокового меню — он
фильтрует и «Смены», и «Дашборд». Выбор сохраняется между заходами; при одной
студии список не показывается.

## Доступ в админку

Вход по логину и паролю. Логин задаёт владелец, пароль — **четыре цифры** —
генерируется при выдаче доступа и показывается ровно один раз; в базе лежит
только хеш (PBKDF2-HMAC-SHA256). Короткий пароль защищён от перебора
блокировкой: после 5 неверных паролей подряд вход по этому логину закрыт на
15 минут, а выдача нового пароля снимает блокировку сразу. Забытый пароль не восстанавливается: администратор
нажимает «Сбросить пароль», получает новый и передаёт его сотруднику; все
прежние сессии этого человека сразу перестают работать.

Пользователь один на все продукты: вошёл — видит и «Скрипты», и
«Аналитику». Права у продуктов свои, их задаёт **владелец** в разделе
**Сотрудники** (внизу бокового меню, рядом с именем вошедшего; раздел виден и
доступен только владельцу): клик по сотруднику открывает окно,
где в одном месте собраны имя, вход, пароль и права по продуктам.

| Продукт | Право | Что разрешает |
|---|---|---|
| Скрипты | чтение | искать, читать и копировать скрипты |
| Скрипты | чтение и правка | ещё добавлять, менять и удалять скрипты и разделы |
| Аналитика | только свои смены | смены, где стоит его имя; ничего не настраивает |
| Аналитика | все смены · администратор | все смены; метрики, промпты, точки, приложение, удаление и пересчёт смен |

Права независимы: администратор ресепшена может править скрипты, не видя
чужих смен, а аналитик — видеть все смены, не трогая тексты. Владелец
(`ADMIN_API_TOKEN`) может всё. Нужна миграция `011_scripts_access.sql`: тем,
у кого был доступ «все смены», она сразу выдаёт правку скриптов, чтобы после
обновления никто не потерял права, которые у него уже были.

`ADMIN_API_TOKEN` остаётся мастер-ключом владельца: им заходят, пока в системе
нет ни одного логина, и им же возвращаются, если пароль последнего
администратора потерян. Сессии подписываются `AUTH_SECRET` (если не задан —
берётся `ADMIN_API_TOKEN`).

## Согласен / не согласен и договорённости

Разбор делает модель, а работать по нему человеку. Поэтому у каждой оценки
внутри разбора есть кнопки «согласен / не согласен»: фиксируется, кто возразил
и когда, к несогласию можно добавить одну фразу пояснения.

Голос всегда относится к конкретной оценке. Общего «согласны с разбором
разговора?» нет намеренно: возражение «вообще» нечем починить — править можно
только промпт той метрики, к которой оно относится.

Несогласия копятся **в разрезе метрики** и показываются в разделе «Метрики и
анализ» рядом с её промптом — со ссылкой на день и разговор, где возразили.
Метрика, с оценками которой спорят на разных сменах разные люди, почти
наверняка сформулирована неточно: это очередь на правку промптов, а не жалобы.

По итогам разбора записываются **договорённости** — одна конкретная вещь,
которую менеджер сделает в следующую смену. В карточке следующей его смены
незакрытые договорённости показываются сверху с вопросом «сделали?», где и
отмечаются: выполнено, не выполнено или снято. Проверка всплывает сама в
нужный день, помнить о ней не нужно.

```bash
cd desktop
npm install
npm run tauri dev            # разработка
npm run build:mac            # сборка под архитектуру этой машины
npm run build:mac:universal  # сборка сразу под Apple Silicon и Intel
```

Готовое приложение: `desktop/src-tauri/target/release/bundle/`
(`macos/Audio Recorder.app` и `dmg/`), для универсальной сборки —
`target/universal-apple-darwin/release/bundle/`.

#### Маки на Intel

Обычная сборка содержит только архитектуру машины, на которой собиралась.
Приложение, собранное на Apple Silicon, **на Intel не запустится**: Rosetta
переводит только в одну сторону — Intel-код на Apple Silicon, не наоборот.

Один раз на машине сборки:

```bash
rustup target add x86_64-apple-darwin aarch64-apple-darwin
```

Дальше собирать `npm run build:mac:universal` — получается один `.app` под обе
архитектуры. Скрипт в конце печатает `lipo -archs`, там должно быть
`x86_64 arm64`.

Требуется macOS 11 Big Sur или новее (`minimumSystemVersion` в
`tauri.conf.json`) — это Intel-маки примерно с 2013 года. Версия проверяется
в «Об этом Mac».

Адрес сервера и ключ приложения вшиваются в сборку — через файл
`desktop/src-tauri/build.env` (копия `build.env.example`) или переменными
окружения:

```bash
AA_SERVER_URL=https://api.example.com AA_APP_KEY=<APP_KEY> npm run build:mac:universal
```

Пошаговая инструкция по сборке для владельца — [docs/BUILD_APP.md](docs/BUILD_APP.md).

После этого в приложении остаётся **одна** настройка — «Точка продажи»:
сотрудник выбирает свою студию из списка и больше в настройки не заходит.
Если сборку сделали без этих переменных, адрес и ключ вводятся один раз в
разделе «Для настройщика».

На главном экране до начала записи видно, **какая студия** и **какой микрофон**
выбраны, и там же **живая полоса уровня**: приложение слушает микрофон, ничего
не записывая, поэтому «слышно или нет» проверяется до нажатия «Начать», а не
через десять секунд после. Ошибку в этих строках надо заметить до смены, а не
при разборе пустой дорожки. Приложение включает **автозапуск при входе в систему** — на
ресепшене его никто не «запускает», оно должно быть открыто с утра само
(переключатель в настройках).

Кнопки: начать день / пауза (личный разговор) / завершить день (дозагрузка
чанков; разбор запускается отдельно, из админки).

**Запись идёт по часам.** Пауза, пропавший микрофон и перезапуск после вылета
пишутся в дорожку тишиной, а не вырезаются: «14:32» в отчёте — это 14:32 на
часах студии, и рядом с каждым разговором админка показывает время на часах.
VAD тишину выбрасывает, так что распознавание она не удорожает.

**Микрофон переоткрывается сам.** Если колонку выдернули или Bluetooth
отвалился, поток с микрофона умирает молча; приложение это замечает за три
секунды, показывает жёлтое предупреждение и пробует открыть микрофон снова,
пока не получится. Для стойки всё равно лучше USB, а не Bluetooth.

**«Завершить» нельзя потерять.** Если в момент завершения сервер недоступен,
запись останавливается, а смена остаётся на экране в состоянии «отправляем»:
сегменты лежат на диске, загрузчик пробует снова, кнопка повторяет попытку.
Смены прошлых дней, которые так и не закрылись (компьютер выключили и ушли),
приложение досылает и закрывает само при следующем запуске — на экране в это
время висит плашка «прошлые смены ещё отправляются».

**Ноутбук на стойке.** `caffeinate` не даёт машине заснуть от бездействия, но
не спасает от закрытой крышки: MacBook должен стоять с открытой крышкой и на
зарядке. После перезагрузки приложение откроется само, но запись начнётся
только по кнопке «Начать».

**Просто так не закрывается.** И крестик, и ⌘Q перехватываются: приложение
задаёт два вопроса подряд, во втором прямо написано, что прервётся и что
последние несохранённые минуты пропадут. Компьютер стоит на ресепшене, за ним
весь день ходят люди, а о случайно закрытом приложении узнают вечером — по
пустой смене.

**Обновляется само.** Владелец собирает новую версию и выкладывает два файла
(архив и подпись) в админке, в разделе «Приложение»; на ресепшенах появляется
плашка «Вышла новая версия» и кнопка «Обновить и перезапустить». Обходить
студии не нужно. Каждая сборка подписана приватным ключом владельца, а
публичный вшит в приложение — подменённый ответ сервера установить чужой код
не заставит. Во время смены кнопка заблокирована: перезапуск оборвал бы
запись.

Первый запуск после обновления показывает зелёную плашку с просьбой проверить
микрофон. Причина в macOS: разрешение выдано подписи бандла, а у самодельной
подписи она меняется с каждой сборкой, так что система может спросить доступ
заново — и смена, записанная мимо этого вопроса, будет тишиной.

- **macOS без подписки Apple Developer:** собирать локально на Mac
  (`signingIdentity: "-"` уже настроен) и переносить `.app` через
  AirDrop/флешку. На машине, куда перенесли, macOS пометит приложение
  карантином и откажется его открывать («повреждено»), потому что подпись
  ad-hoc, а не Developer ID. Снимается один раз:
  `xattr -cr "/Applications/Audio Recorder.app"`.
- **Доступ к микрофону выдаётся заново на каждой машине** — при первом запуске
  система спросит разрешение. Если окно не появилось, проверить
  «Системные настройки → Конфиденциальность и безопасность → Микрофон».
- **Windows без сертификата:** в SmartScreen «Подробнее → Выполнить в любом
  случае».

## Как работает пайплайн обработки

1. Клиент грузит Opus-чанки → по «Завершить день» сервер ставит задачу в Celery.
2. Чанки склеиваются (ffmpeg, один проход перекодирования в единый поток),
   считается длительность.
3. **Silero VAD** находит речевые участки; тишина/музыка выбрасываются
   (обычно остаётся 2–4 ч из 12). Файл читается блоками, поэтому память
   воркера не зависит от длины смены.
4. Речевые участки вырезаются **по сэмплам** и склеиваются в один файл, который
   уходит в **ElevenLabs Scribe** (диаризация + пословные таймкоды); таймкоды
   маппятся обратно на исходную запись без накопления ошибки. Расшифровка с
   таймкодами по исходной записи сохраняется в R2 — пересчёт её переиспользует.
5. **Claude, этап 1** (`dialog_segmentation`): транскрипт дня → список диалогов
   с типами (продажа/консультация/отказ/сервис/нерелевантно). День уходит в
   модель **блоками** (`LLM_STAGE1_BLOCK_CHARS`), разрезанными только по паузам
   длиннее `CONVERSATION_GAP_S`, чтобы ни вход, ни ответ не упирались в лимиты
   запроса; ответ не в JSON запрашивается повторно.
6. **Claude, этап 2** (`sale_analysis`): каждый значимый диалог → чек-лист
   этапов скрипта (✅/⚠️/❌) с дословными цитатами и таймкодами, исход, число
   апсейлов, эффективность.
7. **Claude, reduce** (`daily_summary`): метрики дня + все разборы → главные
   отклонения, рекомендации, предложения по скрипту.
8. Дашборд показывает отчёт; клик по цитате/таймкоду проигрывает аудио с этого
   места (presigned URL из R2; протухшая ссылка обновляется сама). Запись
   лежит в Ogg Opus — Safari его не играет, отчёты слушают в Chrome, Edge
   или Firefox, о чём страница предупреждает.

Нерелевантные (личные) разговоры классифицируются, но их текст не сохраняется.
